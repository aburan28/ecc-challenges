NVIDIA GPU, with Docker

Needs Docker and the NVIDIA Container Toolkit. Save your key to ~/.config/ecc-challenges/api-key (mode 0600) first.

{% if sigma_worker %}

DP30, DP32 and DP34 are Hamming-weight thresholds for distinguished points. DP34 is recommended for new NVIDIA workers and reports points more often. All three can match compatible points from the earlier ECC2K-130 search.

Use a separate state directory for each threshold. Resume an existing run with its original command and directory. The CPU and Mac workers below run protocol 2 and ignore this setting.

{% endif %} 
# one directory per GPU; keep it between restarts
GPU_ID=0
CAMPAIGN={{ selected_campaign|default("ecc2k-130") }}
{% if sigma_worker %}DP_WEIGHT={{ selected_dp_weight }}
{% endif %}WORKER="ecc-gpu-$CAMPAIGN{% if sigma_worker %}-dp$DP_WEIGHT{% endif %}-$GPU_ID"
mkdir -p "$PWD/ecc-data-$CAMPAIGN{% if sigma_worker %}-dp$DP_WEIGHT{% endif %}-$GPU_ID"

docker run -d --name "$WORKER" --stop-timeout 120 \
  --gpus all --restart unless-stopped \
  --user "$(id -u):$(id -g)" \
  -e ECC_GPU="$GPU_ID" \
  -e ECC_CAMPAIGN="$CAMPAIGN" \
  -e ECC_PROTOCOL={{ 1 if sigma_worker else 2 }} \
{% if sigma_worker %}  -e ECC_DP_WEIGHT="$DP_WEIGHT" \
{% endif %}  -e ECC_API_URL=https://ecc-challenges.com \
  -v "$HOME/.config/ecc-challenges/api-key:/run/secrets/ecc_api_key:ro" \
  -v "$PWD/ecc-data-$CAMPAIGN{% if sigma_worker %}-dp$DP_WEIGHT{% endif %}-$GPU_ID:/data" \
  {{ worker_image }}

docker logs --tail 100 -f "$WORKER"
  • For more GPUs, start one container per card with a different GPU_ID and its own state directory. Never reuse or wipe a directory while its run is active.

  • On an x86-64 machine without a GPU, use this same command without --gpus all and -e ECC_GPU; it runs on the CPU. OMP_NUM_THREADS limits the threads.

CPU, with Docker (x86-64 or arm64)

The smaller CPU image runs all 24 curves on either architecture, including Graviton instances. Save your key to ~/.config/ecc-challenges/api-key first.

CAMPAIGN={{ selected_campaign }}
WORKER="ecc-cpu-$CAMPAIGN"
mkdir -p "$PWD/ecc-cpu-$CAMPAIGN"

docker run -d --name "$WORKER" --stop-timeout 120 --restart unless-stopped \
  --user "$(id -u):$(id -g)" \
  -e ECC_BACKEND=cpu -e ECC_PROTOCOL=2 \
  -e ECC_CAMPAIGN="$CAMPAIGN" \
  -e ECC_API_URL=https://ecc-challenges.com \
  -v "$HOME/.config/ecc-challenges/api-key:/run/secrets/ecc_api_key:ro" \
  -v "$PWD/ecc-cpu-$CAMPAIGN:/data" \
  {{ cpu_worker_image }}

docker logs --tail 100 -f "$WORKER"

Native worker

Windows 10 or 11, x64 or ARM64. Runs on the CPU, or on an NVIDIA GPU (x64 only) if the CUDA toolkit is installed. In PowerShell:

# once: Python, CMake and the C++ build tools
winget install -e --id Python.Python.3.12
winget install -e --id Kitware.CMake
winget install -e --id Microsoft.VisualStudio.2022.BuildTools --override "--quiet --wait --add Microsoft.VisualStudio.Workload.VCTools --includeRecommended"

# then, in a new PowerShell window
{{ ps_env }}irm https://ecc-challenges.com/install.ps1 | iex

The installer asks for your key, saves it where only you can read it and offers to start the worker. Stop it with Ctrl-C.

NVIDIA GPU, with Docker Desktop

Install Docker Desktop with the WSL 2 backend and a current NVIDIA driver. Then open an Ubuntu (WSL) terminal, save your key to ~/.config/ecc-challenges/api-key and run the Docker command from the Linux tab.

The same worker, packaged for long-running setups. Running a worker has each recipe.

  • Docker Compose: several workers on one machine.
  • systemd: a Linux server, started at boot, no containers.
  • Kubernetes, Podman, Slurm.
  • Modal, RunPod or any GPU cloud: use the Docker image above, mount persistent storage at /data, and pass the key as a mounted file or the ECC_API_KEY secret.

Docker workers run in the background. Ctrl-C stops following the logs. Pause with docker stop "$WORKER" and resume the same container with docker start "$WORKER"; keep its state directory. If the container name already exists, resume it instead of running the creation command again. For native workers, Ctrl-C stops the worker; use the installer's printed command to resume. A 429 or 503 response makes the worker wait and retry with unsent points kept on disk.
