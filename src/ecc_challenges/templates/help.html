Help with your worker

Start with the worker log and the run's page on your dashboard. Keep the worker's state directory between restarts; it holds the run ID and checkpoint.

Before changing anything

Write down the challenge ID, run ID, worker image digest or version, operating system and the exact error line. Keep the log lines around it and the time it happened.

Keep API keys, authorization headers and signed upload URLs private. Never delete a checkpoint or state directory to get past an error.

Common problems

The worker exits with gateway HTTP 401 or contributor API key is invalid

The gateway did not accept the API key. Open your dashboard and check that the key is listed and not revoked; create a new one if needed. Check that the worker reads the file you expect (~/.config/ecc-challenges/api-key, mounted at /run/secrets/ecc_api_key in Docker) and that the file holds only the key, starting ecc1_. Restart the worker with the same state directory; local state is kept.

The worker says provide the API key by file or environment, not both

Both ECC_API_KEY and a key file are set. Unset ECC_API_KEY or remove the key-file mount, then start the worker again.

The log shows upload-paused, or the points count has not changed

An upload-paused event with status 429 or 503 (upload pending on protocol 1 workers) means the gateway asked the worker to back off. Leave it running: it retries on its own and keeps unsent points on disk. If the count stays flat and the log shows no errors, the worker has not found a distinguished point yet; on larger curves the first one takes longer. Check the challenge on the status page, which refreshes about once a minute.

The run shows Disconnected or the key shows Offline

No heartbeat has arrived for three minutes. Check that the worker process or container is still running (docker ps, docker logs) and that the machine can reach https://ecc-challenges.com. Restart it with the same state directory.

The run shows Reporting unavailable

The worker is too old to send per-run health reports. Update it and keep the state directory: rerun the native installer, or recreate the container with the image from your dashboard. See worker health.

Docker says the container name is already in use

The container from your first docker run still exists. Find it with docker ps -a (dashboard commands name it ecc-gpu-… or ecc-cpu-…) and resume it with docker start <name> instead of running the creation command again.

A worker will not resume

Use the same state directory, challenge, protocol and distinguished-point threshold that started the run. The worker's message says which one differs:

  • state directory belongs to another campaign or another namespace: set ECC_CAMPAIGN back to the challenge that created the directory, or use a new directory for the new challenge.
  • existing run has a different reporting threshold: set ECC_DP_WEIGHT back to the run's value, or use a new directory.
  • worker and gateway namespaces differ; update the pinned image: for Docker, remove the container and recreate it with the image digest on your dashboard and the same state directory (docker restart keeps the old image). For a native install, rerun the installer.
  • run is closed: the run was retired with ECC_ACTION=close. Keep that directory as a record and start a new run in a new one.
  • public worker failed (BlockingIOError: …) right after start (a PermissionError or OSError on Windows): another worker holds the directory's lock. Stop the duplicate; only one worker may use a directory at a time.

If a message asks you to preserve state for recovery, stop the worker and leave the directory untouched. The cloud guide covers persistent volumes on Modal and RunPod.

A result or count looks wrong

Archived points and independently verified work are different counts. The status page explains each figure, and open problems lists known validation and capacity gaps. Solved challenges link to their published key and public point from the challenge tables.
