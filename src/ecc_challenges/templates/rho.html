How it works

Pollard rho, and making each step cheap

The search is one idea from 1978, spread over many machines, with the arithmetic tuned down to the bit. This page explains the method, how the site estimates work done, and what the kernels do to keep every step short.

The problem

Each challenge fixes an elliptic curve, a base point G of prime order n, and a target point Q. The answer is the integer d with Q = dG. Computing dG from d takes a few hundred point operations. Going back from Q to d is the elliptic-curve discrete logarithm problem, and for a well-chosen curve nothing known beats a generic search.

The best generic search needs about √n operations. That is why sizes are quoted in bits: a curve with a 130-bit group order costs roughly 265 steps before any of the savings below, and every extra 2 bits doubles the work.

Pollard's rho

Pick a function f that maps points to points and looks random, but where every point it produces is a known combination aG + bQ. Start somewhere and iterate: Ri+1 = f(Ri). The group is finite, so the walk must eventually repeat a point. From then on it loops, and the path traced out looks like the Greek letter ρ.

At the repeat, two different combinations name the same point: aG + bQ = a′G + b′Q. Since Q = dG, that gives d ≡ (a − a′) / (b′ − b) mod n, unless b = b′, which is vanishingly unlikely.

How long until the first repeat? It is the birthday problem. If f behaves like a random function on a set of size N, the expected number of steps is

E = √(πN/2)

and the chance of having seen a repeat after k steps is about 1 − exp(−k²/2N). Rho needs almost no memory, which matters as much as the step count: baby-step giant-step has the same running time but would have to store about √n ≈ 264 points.

Real walks are not truly random. The usual choice, an r-adding walk, splits the curve into r classes by a hash of the point and adds a fixed precomputed point for each class. With enough classes it behaves close to random; the all-curve worker here uses 32.

Many walks at once

One walk cannot be split across machines, but many walks can share one search. If two walks ever land on the same point they stay together from then on, because f is deterministic. A collision between any two walks is as useful as a walk meeting itself, so m machines finish about m times faster.

The trick, from van Oorschot and Wiener, is to report only rare distinguished points: points with an easily tested property, such as a run of zero bits. Each walk runs until it hits one, uploads it with its coefficients, and carries on. When two walks merge, they reach the same distinguished point soon after, and the server sees the same point arrive twice.

If a fraction p of points are distinguished, each walk uploads a point every 1/p steps on average, and a merge is noticed about 1/p steps after it happens. Workers choose p small enough that the uploads stay manageable and large enough that the steps still running inside unfinished walks are a small share of the total.

Fewer points to search

Rho's cost depends on the size of the set it walks on, so any way to make the walk treat several points as one helps. Every curve has the negation map: P and −P share an x-coordinate. A walk on the pairs {P, −P} searches a set half the size, which saves a factor of √2.

Koblitz curves such as ECC2K-130 have more. Their equation has coefficients in GF(2), so the Frobenius map σ(x, y) = (x², y²) sends curve points to curve points, and on the prime-order subgroup it acts as multiplication by a fixed scalar. Applying σ 131 times returns to the start, so each point has 131 Frobenius images and 262 once negation is included. A walk on those classes saves a further factor of √131 ≈ 11.4.

These savings are exactly what separates Certicom's estimates from the plain √(πn/2). For ordinary curves Certicom uses √(πn/4), with negation; for Koblitz curves over GF(2m) it uses √(πn/4m), with negation and Frobenius. For ECC2K-130, with n ≈ 2129, that is 260.81 ≈ 2.0 × 1018, the figure in its table.

On this site. The ECC2K-130 GPU worker walks on the 262-point classes, so its expected work is Certicom's 260.8. The newer all-curve worker uses a plain 32-way adding walk with no automorphism quotient yet, so its expectation is √(πn/2), a factor of √2 (or √(2m) on Koblitz curves) above Certicom's figure. Each challenge page shows both numbers. Folding the negation map into that walk without falling into short fruitless cycles is known, fiddly work, and a good place to contribute.

The ECC2K-130 walk

ECC2K-130 is the curve y² + xy = x³ + 1 over GF(2131), with 4n points and n ≈ 2129 prime. The GPU worker uses the walk from Bailey et al.'s Breaking ECC2K-130:

R′ = R + σj(R),   j = 3 + (HW(x)/2 mod 8)

Here HW(x) is the Hamming weight of the x-coordinate written in a normal basis, so j runs from 3 to 10. In that basis σ only permutes the bits of x, and negation leaves x alone, so all 262 points of a class have the same weight and take the same step. The walk is therefore well defined on classes without ever computing a canonical representative inside the loop. That is where the √262 saving comes from, at the cost of one Frobenius map per step.

  • Start points. A walk starts at Q plus a sum of σi(P) chosen by 128 pseudo-random bits of its 64-bit seed. The seed packs a 16-bit run ID, a 32-bit lane number and a 16-bit restart counter.
  • No coefficients on the GPU. σ acts on the subgroup as multiplication by a fixed scalar s, so each step multiplies the point's logarithm by 1 + sj. The GPU carries nothing but the point. When two seeds reach the same distinguished point, the server replays both walks, counts how often each j was taken, and solves for d.
  • Distinguished points. A point is distinguished when HW(x) ≤ 32, about one point in 228.41. The worker uploads 32 bytes: the seed, and x replaced by the smallest of its 131 Frobenius conjugates so that every member of a class gives the same key.
  • No cycle detection. A lane that walks 232 steps, about twelve average trails, without reaching a distinguished point restarts from a new seed. That cuts about 0.0006% of honest trails.

Estimating work done

The server never sees individual steps, only distinguished points. But every step has the same chance p of landing on one, so D stored points stand for about D/p steps. The site reports work this way, as a power of two.

The distinguishing probability

On the ECC2K-130 walk, a point is distinguished when its normal-basis x-coordinate has Hamming weight 32 or less. For points in the subgroup that weight is always even, so the x-coordinates are spread over the 2130 even-weight 131-bit strings, and

p = ( C(131, 0) + C(131, 2) + … + C(131, 32) ) / 2130 ≈ 2−28.41

so each stored point stands for about 228.41 ≈ 356 million steps. On the all-curve walk a point is distinguished when d chosen bits of a SHA-256 hash of the point are zero, so p = 2−d; d is set per curve and recorded with every batch.

Work and odds

With k = D/p steps done and an expected E, the share of expected work is k/E, and the chance that rho would have produced a collision by now is

P(k) ≈ 1 − exp(−(π/4)·(k/E)²)

What the estimate assumes

  • Points come from honest walks. Sampled replays and per-point checks make cheating expensive, but a stored point is not a proof of the steps behind it.
  • The walk is close to random. Practical walks, with a fixed set of jumps chosen by a few bits of the point, need slightly more steps than a truly random function, so the odds shown are a little optimistic.
  • Only steps that end at a stored point count. A large GPU keeps hundreds of thousands of walks going, each a few hundred million steps from its next report, so the figure lags the hardware. Steps in walks abandoned before they report are never counted, and could not have produced a detectable collision either.
  • Separate walks on the same curve, such as the GPU walk and the all-curve walk on ECC2K-130, cannot collide with each other. Their work adds, and their odds combine as independent searches.

Inside the kernels

Across the whole search the GPU client performs the same step about 261 times, so the work is all in making that step short. Each step costs five field multiplications, one squaring, a Frobenius map, a Hamming weight, and a sixteenth of an inversion. The techniques below come from the client's source, vendored at a pinned commit in vendor/cryptanalysis/ecc2k130, and the figures from its comments and benchmarks.

Two bases, each where it is cheap

In a normal basis, squaring and σj are fixed bit permutations and the Hamming weight is a popcount, but multiplication is awkward. In a polynomial basis, multiplication is an ordinary carry-less product. The kernel keeps x and y in a polynomial basis (powers of β1 modulo its 19-term minimal polynomial) and converts to the normal basis each step for the weight and the Frobenius map. The conversions are generated linear maps written as log-depth shift, mask and XOR stages, and the unreduced 261-bit product converts straight to the normal basis with no separate reduction.

packedtransform131.h · packedgeneratedproduct131.h
1.8× on L4 and L40S

Carry-less multiply on the FP64 pipe

On sm_80 and newer, each 64 × 64-bit carry-less product is two inline PTX clmad.lo.u64 / clmad.hi.u64 instructions. One level of Karatsuba gives the 128 × 128-bit core in six of them, and the remaining three bits are handled with masked shifts. A clmad is dearer than the roughly 22 logic operations it replaces, but it runs on the FP64 pipe: Nsight puts the integer pipe at 87.3% and the FP64 pipe at 51.4%, so moving work across pays. The same reasoning turns squaring's bit spread into clmad.lo(x, x). Measured against the software product, the clmad build is 1.811× faster on an L40S and 1.881× on an L4.

packed131.h

A software product from integer multiplies

Turing GPUs have no carry-less multiplier. There, a 32 × 32-bit carry-less product splits each operand into four "holed" parts, with every fourth bit kept (masks such as 0x11111111), and multiplies them as integers: no column can collect enough carries to reach the next kept bit, so 16 integer multiplies and some masking give the exact result. Karatsuba builds 64- and 128-bit products from those.

packed131.h · clmul32, clmul64, clmul128

Frobenius as a permutation network

σj is applied with a generated network of 56 masked swap stages, each t = ((v >> s) ^ v) & mask; v ^= t ^ (t << s) with s in 1, 2, 4, 8, 16, plus whole-word exchanges. There is one column of masks per j from 3 to 10. Each block copies those 448 mask words into shared memory, and a paired network applies one mask load to x and y together.

packedsigma131.h

Sixteen walks per inversion

Adding two affine points needs an inversion, which costs as much as several multiplications. Montgomery's trick inverts the product of sixteen denominators once and recovers each one's inverse from it, for about three extra multiplications per walk. The kernel's weighted variant stores Ei · ∏k<i Dk on the way forward, so the reverse pass gets each slope λi in one product.

packedkernels.cuh · kernel.h (ECC_BATCH = 16)

An inversion in eight multiplications

The shared inversion uses Itoh–Tsujii: a−1 = (a2130 − 1)², built along the chain 1, 2, 4, 8, 16, 32, 64, 65, 130 with eight multiplications. The raising to 2k between them would be k squarings, but in the normal basis it is σk, a single permutation, so it reuses the same networks with masks for k = 16, 32 and 65 in constant memory.

packed131.h · inv131

Seventeen bytes per field element

A 131-bit element would take five 32-bit words. The compact state stores it as a 16-byte record, loaded and stored as one uint4, and a separate byte holding the top three bits, laid out thread by thread so a warp's accesses coalesce. Each 256-thread tile and walk slot takes 4,352 bytes. Spare bits in the denominator's top byte carry j − 3, so the reverse pass does not recompute it.

packedcompactstate.cuh

Keeping the working set in L2

x, y, the prefix chain and the denominators share one allocation, so a single cudaAccessPolicyWindow can mark it persisting in L2, an 80 MiB window on an RTX PRO 6000. The 128 precomputed σi(P) used for start points, and Q, sit in constant memory.

ec2k_gpu.cu

Registers, occupancy and code size

The campaign preset launches 256-thread blocks with __launch_bounds__(256, 2), two per SM, sized from the occupancy API. Field values pass by value so they stay in registers, the large routines are __noinline__ so only one copy of each is in the instruction stream, and the slot loops stay rolled. Weights use __popc; the compiler already turns the XOR-and-mask chains into three-input LOP3 instructions.

kernel.h · Makefile (WALK=sigma) · packed131.h

Reporting without divergence

A lane that reaches a distinguished point claims a slot in a 218-entry buffer with one atomicAdd, writes its record and is marked dead. It keeps doing the same arithmetic as its warp until the next launch reseeds it, so a report never splits a warp's control flow.

packedkernels.cuh

Losing at most a minute

Every 60 seconds, and on SIGTERM, the client fsyncs its points, writes the walk state to a temporary file, fsyncs it, renames it into place and fsyncs the directory. A preempted cloud GPU resumes where it stopped. A separate health mode runs at weight 42 and checks every report against the curve; a single flipped bit leaves the rest of the trail off the curve, so a bad card is caught quickly.

ec2k_gpu.cu · healthcheck.h

For scale, the source records a tuned build of this walk at about 15.4 billion steps a second on one RTX PRO 6000. At that rate the expected 260.8 steps is about four GPU-years.

The all-curve engine

Every other challenge, and every CPU, macOS and Windows worker, uses a separate portable engine that puts correctness first. It walks a 32-way adding walk in affine coordinates with up to 359-bit fields in twelve 32-bit limbs, picks the jump and tests for a distinguished point from one SHA-256 of the point, and carries the coefficients a and b so every report can be checked on its own. Each step does a full point addition with its own inversion, using bit-serial modular multiplication and an extended Euclidean inverse. It builds for CUDA, for CPUs with OpenMP, and for Metal, where the shader is compiled at run time and each command buffer runs at most 16 steps to stay under the macOS GPU watchdog.

That leaves a lot on the table, and most of it is described above: batched inversion, Montgomery or Karatsuba multiplication, carry-less instructions for the binary curves, and the negation and Frobenius maps. Each is a self-contained place to contribute.

Checking the work

Fast code is only useful if its output is right, and a distributed search has to assume some workers are faulty or dishonest.

  • ECC2K-130 points are checked for shape on upload: the seed must belong to the run, and x must be under 2131 with even weight of at most 32. The first batch of every run, and 1 in 128 later batches, is sent to an audit pool that replays one record from its seed on an independent reference implementation of the walk and compares the 32 bytes exactly.
  • All-curve points are each checked: the point is on the curve, it is distinguished, R = aG + bQ holds, and b matches the walk's start. Workers run the same checks before uploading.
  • A failed check suspends the run, revokes its key and removes its points from collision search.
  • A collision is recomputed from both walks, the scalar is solved, and the reference code checks dG = Q before anything is announced.
