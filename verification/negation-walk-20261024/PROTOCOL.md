# PROTOCOL: negation-class walk vs the v2 adding walk (frozen before any data)

Frozen 2026-10-24, before the first measurement. The SHA-256 of this file, of
the scripts and of the code under test is in `FREEZE.sha256`, written first.
Nothing below is changed after data exists; a deviation is recorded in
`README.md` under "Deviations" with its reason, and the frozen rule still
stands as the reported verdict.

## 1. Question

Does the negation-class walk (`certicom-affine-negation-class32-v1`, ECCJOB04,
described in `docs/negation-walk.md`) need fewer steps per solve than the
current v2 adding walk (`certicom-affine-radding32-v2`, ECCJOB03) on the same
planted instances, and how much slower is one step? Expectation stated by the
requester: about 0.71x the steps (1/sqrt(2) = 0.7071) at a small rate loss.
A null or negative result is a valid, recorded outcome.

## 2. Arms

| arm | walk | job selector | role |
| --- | --- | --- | --- |
| A | v2 adding walk | ECCJOB03, reserved 0 | baseline |
| B | negation-class walk, full | ECCJOB04, reserved 1 | candidate |
| A2 | v2 adding walk, independent seeds | ECCJOB03 | A/A null control |
| C | negation-class walk without look-ahead and cycle handling | reserved 2 (driver only, the engine file parser refuses it) | positive control: a known large effect the detector must see |

All arms run the same C++ code the CPU engine and the CUDA kernel use
(`worker/generic/ec_core.h`, through `worker/generic/solve_bench.cpp`, which
includes `engine.cu`), single thread, `g++ -std=c++17 -O2` (the Dockerfile.cpu
flags without OpenMP).

## 4. Parameters (fixed)

* 8 lanes, rounds of 256 steps (the worker default `ECC_STEPS_PER_ROUND`).
* DP bits per arm: d = max(2, floor(log2 E_arm) - 6) with E_A = E_A2 =
  sqrt(pi n / 2) and E_B = E_C = sqrt(pi n / 4); a trail is restarted when it
  reaches 32 * 2^d steps, as the worker does. d values: primary 5/5, 8/7, 9/9,
  11/11 (A/B); secondary 6/5, 7/7, 10/9.
* Every DP is entered into a table keyed by the stored point (x, y). The first
  pair with equal points, different (a, b), b1 != b2 ends the solve; the solved
  scalar (a1 - a2)/(b2 - b1) must equal the planted d (any other value voids
  the arm).
* Steps per solve are counted in lockstep time: all lanes are assumed to
  advance together, and the count is the sum over lanes of the steps each had
  taken at the step of the second DP. DPs inside a round are ordered by their
  step within the round. Look-ahead retries and escape moves are steps of the
  walk (one transition each); the point additions they cost are counted
  separately.
* Give-up limit: 300 * sqrt(pi n / 2) physical steps; gave_up solves are
  reported and counted as failures, never dropped.
* Seeds: arms A, B, C 20261024; arm A2 20261025; solve indices 0..N-1.
* Rate measurement: `solve_bench rate`, 16 lanes, rounds of 256 steps, DP bits
  40 (no trail ends), 15 repetitions per arm alternated A,B,B,A,... per curve,
  16384 steps per lane on toy-prime-24-0, toy-prime-35-3, toy-binary-33-2 and
  4096 on eccp-79 and ecc2-79 (real Certicom fields, rate only). The unit cost
  of one affine group addition is the median of 5 runs of `solve_bench addtime`
  (100000 dependent additions).

## 5. Measures and decision rules

M1. R = mean steps(B) / mean steps(A) per instance, with a 95% bootstrap
percentile interval (10000 resamples, seed 1, the two arms resampled
independently). Pooled over the four primary sizes: the geometric mean of the
four R, interval from the same resamples.

* **Verified step reduction at a size:** the upper end of its interval is below 1.
  **Verified overall:** all four primary sizes verified.
* **Consistent with theory at a size:** its interval contains 1/sqrt(2) = 0.7071.
  Sizes outside are reported with the distance, not explained away.
* If the interval contains 1 the result at that size is "no verified step
  reduction".

M2. Rate loss per step = 1 - (median ns/step of A) / (median ns/step of B),
with a 95% bootstrap interval over the repetitions. Net time ratio = R * (ns/step
B / ns/step A) per instance; for curves without a solve measurement it is
reported only as a projection with the pooled R and labelled as such.

M3. Native overhead in group-addition equivalents (GAE): ((ns/step B - ns/step A)
- lookahead_retries_per_step * ns_per_addition) / ns_per_addition.

M4. Priced comparison (matched-rho rule, AGENTS.md section 5a of the sibling
repository): the walk's native, unpriced work is the SHA-256 digest (1 per
point addition attempt), the canonical-sign test and negation (1 per addition
attempt, arm B only) and the cycle-window store/check (1 per step, arm B only).
Cost of an arm = group additions + lambda * native operations, per solve, for
lambda = 0, 0.1 and 1 GAE per operation; arm A has 1 addition and 1 native
operation per step, arm B a measured `adds_per_step` a >= 1 and 2a + 1 native
operations per step. Report B/A at the three lambda and the break-even
lambda. The order of the two arms is called settled only where it holds at all
three; otherwise the table says where it flips.

M5. Distance remaining to Pollard rho is not measured here: the matched rho for
these instances is the same sqrt(pi n / 2)-class walk (arm A is plain rho with
an r-adding walk). The report gives each arm's mean steps as a multiple of
sqrt(n) and of the theoretical rho expectation sqrt(pi n / 4) for the class
search.

## 6. Controls and when the harness is void

* **A/A (null):** mean(A2)/mean(A) with a 99% interval at each primary size. The
  harness passes iff all four intervals contain 1.
* **Positive control:** mean(C)/mean(A) at the two positive-control sizes; passes
  iff the lower end of each 95% interval exceeds 2 (without cycle handling the
  negation walk gets trapped in fruitless cycles, a known large effect).
* **Calibration:** mean(A) / sqrt(pi n / 2) reported for every primary size; it
  should lie in [0.8, 1.5] (a sanity gate for the harness, not a result).
* **Integrity:** every solve must return the planted scalar. A wrong scalar,
  a driver error or a missing chunk voids the arm; it is reported, not patched.
* If A/A or the positive control fails, no verdict is drawn from B/A and the
  failure is the result.

## 7. What each outcome means

| outcome | reading |
| --- | --- |
| B/A interval below 1 at every primary size, A/A and C controls pass | the negation walk needs fewer steps on these toy instances; the size of the gap is the interval, reported against 0.7071 |
| interval contains 1 at a size | no step reduction demonstrated there |
| B/A above 0.7071 with the interval excluding it | fewer steps, but less than the quotient predicts: the look-ahead, window and escape overhead and the residual cycle loss are what remains |
| net time ratio >= 1 although B/A < 1 | per-step cost eats the step saving on this CPU; the saving is not a speedup here |
| priced order flips inside lambda 0..1 | the order is not settled across the matched-pricing band; the measured native overhead in GAE/step says on which side this CPU lies |

Scope. These are CPU timings on a shared L0 cloud VM, with the project's generic
bit-serial 12-word arithmetic on toy fields; they say nothing about a GPU, and
the CUDA kernel path is untested here. A saving in steps is not a saving in a
campaign until a negation-walk namespace is enabled and run: its distinguished
points never combine with v2 points.

## 8. Procedure

`python3 run_study.py build|solve|rate|env --work WORK`, each under
`flock .../heavy.lock`, at most about 25 minutes per locked job, resumable (one
output file per chunk of 25 solves or per rate repetition; existing files are
skipped). Two driver processes at most during `solve` (2 cores); `rate` runs a
single process. Interruptions are recorded in `README.md`. `analyze.py` applies
sections 5 and 6 and writes `results/summary.json` and `results/tables.md`.
