# Matched L4 binary rho worker benchmark, 2026-10-19

## Question and decision

Does the bounded-word, branchless `binary_xtime` in commit `213a94f` improve
full CUDA worker invocation time over the shared-header implementation on
`main`? On the longer nine-curve panel it was slower in every matched pair.
The final PR therefore restores the `main` arithmetic. The extra
reference-equivalence self-test and benchmark/replay tooling remain useful.
This decision is limited to the measured L4 workloads; it selects no fleet or
ECDLP cost improvement.

## Frozen controls and execution

- Baseline and candidate used identical `engine.cu` bytes, SHA-256
  `391d46a725d2dc7d63a9eb9bfe94eaf863c83074f54353dcecc9e51d28fcb13e`.
  The archived baseline header hashes to
  `90b2d04da9c626e2d0a0f6e63f3f50929a93b28caf522211bfdae43b414eff80`;
  the candidate header at `213a94f` hashes to
  `bb9bc6721d6162733466ad4d6636709ac1a4934fdb88e57c0236f9b680f1e2b0`.
- Inputs were the nine pinned `mixed-dp40-cpu` `ECCJOB03` job/input pairs from
  `xtime-20261016/cpu-controls.tar.gz`, extracted locally for the image build.
  The launcher deterministically expanded active states to the requested lanes;
  the exact expanded bytes are retained in each run archive. Each repeat ran baseline,
  candidate, baseline on one NVIDIA L4 in the same Modal function/image.
- Image: `nvidia/cuda:13.0.2-devel-ubuntu24.04`, Python 3.12. Compilation:
  `nvcc -std=c++17 -O2 -gencode arch=compute_80,code=compute_80` for each arm;
  both binaries passed `--self-test` during image build. The run receipts record
  driver `610.57.04`, binary hashes, launcher hash, and device telemetry.
  The commands for every worker invocation are in the receipt rows.
- Attempt 1 requested 32 lanes, 64 rounds, two repeats. The image built, but
  remote module import raised `KeyError ECC_BASELINE_HEADER`; it yielded zero
  workload rows. Its log and failure receipt are retained. The launcher was
  fixed by resolving local paths only in the client process.
- Attempt 2 ran 32 lanes, 64 rounds, two repeats: 54 successful invocations,
  18 comparisons, 2,048 actual steps per invocation. The planned follow-up
  (`l4-matched-20261019-attempt3-plan.json`) specified 256 lanes, 512 rounds,
  two repeats, maximum 54 invocations, 120-second invocation timeout, and a
  1.05 maximum baseline-bracket drift for an interpretable speed comparison.
  Attempt 3 met all 54 invocations, with 131,072 actual steps each.
- The timing boundary is full worker process invocation, including startup,
  validation, transfers, CUDA work, and output writing. Worker exit code,
  output bytes, distinguished-point bytes, and step counts agreed exactly
  within every three-invocation pair. `verify_l4_receipt.py` replays all raw
  job/input/output hashes, output lengths, step counters, and pair equality
  from each compressed archive; it verified both completed attempts.

## Observations

Ratios below are candidate elapsed nanoseconds divided by the median of its
two bracketing baseline invocations. Above 1 means the candidate took longer.
Each cell lists the two repeats. The raw nanosecond measurements and baseline
brackets are in `receipt.json`, one row per invocation.

| Curve | 32 × 64 ratio | 256 × 512 ratio |
| --- | ---: | ---: |
| ECC2K-130 | 1.476, 0.998 | 1.572, 1.122 |
| ECC2-131 | 0.915, 1.152 | 1.145, 1.270 |
| ECC2K-163 | 1.220, 1.105 | 1.232, 1.046 |
| ECC2-163 | 1.034, 1.008 | 1.179, 1.153 |
| ECC2-191 | 1.096, 1.038 | 1.148, 1.139 |
| ECC2K-238 | 0.963, 0.856 | 1.184, 1.260 |
| ECC2-238 | 1.050, 1.053 | 1.091, 1.233 |
| ECC2K-358 | 1.216, 1.183 | 1.317, 1.291 |
| ECC2-353 | 1.111, 1.147 | 1.350, 1.360 |

The short panel's pooled median ratio was 1.074; four of 18 pairs were below
1, but those four had baseline-bracket drift above 1.05. Its 12 low-drift
pairs all exceeded 1. The longer panel's pooled median was 1.208; all 18
pairs exceeded 1. Its ten low-drift pairs ranged from 1.122 to 1.360. One
ECC2K-130 repeat had 3.724 baseline drift, so its 1.572 ratio should not be
used alone. Device clocks and process startup can vary, and two repeats per
curve do not quantify long-run fleet variability.

The receipt measures each worker process but does not contain Modal image
build time, GPU allocation time, billed seconds, dollars, or sustained ingest
and collision service costs. Those fields remain unavailable, so the measured
ratios cannot support an end-to-end campaign speed claim. No profiler capture
or instruction export was produced; the mechanism of the slowdown is still
unmeasured. The next useful engineering measurement would separate kernel
time from process overhead and inspect register and instruction changes for
the same pinned workloads before proposing another arithmetic replacement.
